## 문제부터 봅시다

쇼핑몰 장바구니를 클래스로 만들었습니다. 민수(`a`)와 지영(`b`)이 각자 물건을 하나씩 담았는데, 민수의 장바구니를 열어 보니 지영의 우유까지 들어 있습니다. 오류는 하나도 나지 않았습니다.

아래 그림이 그 순간의 메모리입니다. 아직 그림 읽는 법을 몰라도 괜찮습니다. 한 가지만 눈여겨보세요. **장바구니는 두 개인데 배열은 하나이고, 그 배열로 화살표가 여러 개 모여 있습니다.**

이 강의를 마치면 이 그림을 직접 그릴 수 있고, 그림만 보고 원인을 말하고 고칠 수 있게 됩니다. 객체지향을 공부할 때는 **코드를 읽기 전에 그림을 먼저 그리는 습관**이 가장 중요합니다. 객체지향은 문법이 아니라 "무엇이 무엇을 가리키고, 누가 무엇을 책임지는가"에 대한 이야기이기 때문입니다.

## 비유: 물건함, 열쇠 꼬리표, 공용 공구함

- **객체(Object)** 는 **이름 붙은 칸이 있는 물건함**입니다. 칸마다 값이 들어 있거나, 다른 물건함을 가리키는 쪽지가 들어 있습니다.
- **변수**는 물건함이 아니라 물건함에 달린 **열쇠 꼬리표**입니다. `const a = …`는 "꼬리표 a를 어떤 물건함에 건다"는 뜻입니다. 그림에서는 화살표로 그립니다.
- **메서드**는 모든 물건함이 함께 쓰는 **공용 공구함**에 들어 있습니다. 물건함마다 망치를 하나씩 두지 않고 공구함 하나를 같이 씁니다. 이 공구함이 **프로토타입(prototype)** 이고, 그림에서는 점선으로 연결합니다.

<Callout kind="limit" title="이 비유가 맞지 않는 지점">
현실에서 열쇠를 복사하면 "같은 물건함을 여는 열쇠가 두 개"라는 사실을 쉽게 기억합니다. 프로그램에서는 그게 잘 안 보입니다. <code>const empty = []</code>를 두 장바구니에 넘기면 배열이 두 개가 된 것처럼 느껴지지만, 실제로는 꼬리표(화살표)만 늘어나고 배열은 하나입니다. 처음 그림의 버그가 정확히 이것입니다. 또 공구함의 도구(메서드)는 "누구를 위해 일하는지(this)"를 스스로 기억하지 않습니다. 이 차이는 ④에서 다룹니다.
</Callout>

## 정확한 정의: 객체 다이어그램으로 읽기

<OopFigure model="cart" variant="fresh" n={2} at="end" fig="1-1" caption="올바르게 만든 장바구니 두 개. 스택의 이름이 힙의 인스턴스를, 인스턴스의 items가 각자의 배열을 가리킵니다. 두 인스턴스 모두 점선으로 Cart.prototype에 이어져 있습니다." />

Fig 1-1을 기준으로 용어를 정확히 정의합니다.

- **객체(Object)**: 다음 세 요소를 가진 단위입니다. 그림의 상자 하나입니다.
  - **상태(State)**: 상자 안의 칸(속성, property)에 든 값입니다. 예: `owner = "민수"`
  - **행동(Behavior)**: 그 객체에 보낼 수 있는 요청, 즉 메서드(method)입니다. 예: `add()`
  - **정체성(Identity)**: 내용이 똑같아도 다른 상자는 다른 객체입니다. 객체끼리 `===`로 비교하면 내용이 아니라 같은 상자인지(화살표 끝이 같은지)를 봅니다.
- **참조(Reference)**: 객체를 가리키는 값입니다. 그림의 실선 화살표입니다. 변수와 칸에는 객체가 통째로 들어가는 게 아니라 화살표가 들어갑니다.
- **클래스(Class)**: 같은 모양의 객체를 만드는 틀입니다. 어떤 칸을 가질지(필드)와 어떤 행동을 할지(메서드)를 정합니다.
- **인스턴스(Instance)**: 클래스로 만든 객체입니다. 그림의 C0, C1입니다. `a instanceof Cart`가 `true`입니다.
- **프로토타입(Prototype)**: 메서드를 담아 두고 인스턴스들이 함께 쓰는 객체입니다. 그림의 `Cart.prototype`입니다. 각 인스턴스는 내부에 [[Prototype]]이라는 숨은 연결을 가지며, 그림에서는 점선으로 그립니다.
- **스택(Stack)과 힙(Heap)**: 이 강의의 그림에서 왼쪽 열(이름과 실행 중인 함수의 지역 변수)을 스택, 나머지(객체들이 사는 곳)를 힙이라고 부릅니다. 실제 엔진은 더 복잡하지만, "이름은 스택에, 객체는 힙에, 이름은 객체를 가리킨다"는 그림은 그대로 유효합니다.

## 왜 객체지향이 생겼나

데이터와 함수가 따로 있으면, 규모가 커질수록 세 가지 문제가 생깁니다.

1. **누구나 데이터를 바꿀 수 있습니다.** 장바구니 배열이 전역에 있으면 프로그램 어디에서든 그 배열을 비울 수 있습니다.
2. **같은 종류가 여러 개가 되면 짝 맞추기가 어렵습니다.** 장바구니가 1000개가 되면 "어떤 배열이 누구 것인지"를 따로 관리해야 합니다.
3. **변경이 멀리 퍼집니다.** 장바구니 데이터 모양을 바꾸면 그것을 만지는 함수를 전부 찾아 고쳐야 합니다.

객체지향의 해법은 **데이터(상태)와 그 데이터를 다루는 행동을 한 상자로 묶는 것**입니다. 장바구니 객체가 자기 배열을 갖고, 물건을 담는 일은 `add` 요청으로만 하게 하면, 규칙(예: 같은 물건 중복 금지)을 `add` 한곳에만 두면 됩니다.

<Callout kind="note" title="역사 한 줄">
1967년 Simula 67이 시뮬레이션 속 "사물"을 표현하려고 클래스와 객체를 처음 도입했습니다. 1970년대 Alan Kay의 Smalltalk는 "객체끼리 메시지를 주고받는다"는 모델로 이를 발전시켰습니다. JavaScript는 1995년에 Self라는 언어의 영향을 받아 클래스 대신 <strong>프로토타입</strong>으로 객체를 잇는 방식을 택했고, 2015년(ES2015)에 <code>class</code> 문법이 추가됐습니다. 이 문법도 내부적으로는 여전히 프로토타입으로 동작합니다. 그래서 이 강의의 그림에 점선이 등장합니다.
</Callout>

## 내부 동작: 그림이 바뀌는 순서

### 장면 1. new 한 번에 일어나는 네 가지

```ts
const a = new Cart("민수", []);
```

이 한 줄은 그림을 네 번 바꿉니다.

1. **빈 상자를 만듭니다.** 힙에 칸이 하나도 없는 객체 C0이 생깁니다.
2. **점선을 잇습니다.** C0의 [[Prototype]]을 `Cart.prototype`에 연결합니다.
3. **생성자를 실행합니다.** 생성자 안에서 `this`는 방금 만든 C0입니다. `this.owner = owner`는 C0에 칸을 만듭니다.
4. **이름을 겁니다.** 생성자가 끝나면 이름 `a`가 C0을 가리킵니다.

<OopFigure model="cart" variant="fresh" n={2} at="new가 빈 객체 C0" fig="1-2" caption="1~3단계가 시작된 순간. 생성자가 실행 중(constructor() 실행)이며 this가 빈 상자 C0을 가리킵니다. 아직 이름 a는 없습니다." />

<OopFigure model="cart" variant="fresh" n={2} at="이름 a → C0" fig="1-3" caption="4단계. 생성자 프레임이 사라지고 이름 a가 C0을 가리킵니다. C0은 owner와 items 칸만 가지며, add는 갖고 있지 않습니다." />

### 장면 2. 메서드는 점선을 따라 올라가서 찾습니다

```ts
a.add("사과");
```

1. C0에서 `add` 칸을 찾습니다. **없습니다.**
2. 점선을 따라 `Cart.prototype`에서 찾습니다. **있습니다.**
3. 찾은 함수를 실행하는데, 이때 `this`는 호출 식에서 **점 왼쪽에 있던 `a`**, 즉 C0입니다.
4. 함수 안의 `this.items`는 C0의 items 칸을 따라가 배열에 도착하고, 그 배열에 `"사과"`를 넣습니다.

<OopFigure model="cart" variant="fresh" n={2} at="add를 C0에서 못 찾아" fig="1-4" caption="a.add 호출 순간. 굵은 점선이 C0에서 Cart.prototype으로 올라가는 탐색 경로이고, 실행 중인 add()의 this는 C0을 가리킵니다." />

<Callout kind="tip" title="이 강의의 규칙 세 가지">
<strong>읽기</strong>: 객체에서 이름을 찾을 때 자기 칸부터 보고, 없으면 점선을 따라 올라갑니다.<br />
<strong>쓰기</strong>: <code>this.x = …</code> 같은 대입은 점선을 타지 않고 항상 자기 상자에 칸을 만듭니다.<br />
<strong>this</strong>: 정의한 곳이 아니라 <em>호출하는 모양</em>이 정합니다. <code>a.add()</code>처럼 점 왼쪽이 있으면 그것이 this입니다.
</Callout>

### 장면 3. 메서드를 꺼내면 this가 따라오지 않습니다

```ts
const inc = c.increment;
inc();
```

`inc`는 함수 자체를 가리키는 화살표일 뿐입니다. 함수는 자기가 어느 객체에서 꺼내졌는지 기억하지 않습니다. `inc()`에는 점 왼쪽이 없으므로 this를 정해 줄 객체가 없습니다. 클래스 본문은 엄격 모드(strict mode)로 실행되기 때문에 this는 `undefined`가 됩니다.

<OopFigure model="this" variant="detach" at="점 왼쪽이 없음" fig="1-5" caption="inc() 호출 순간. 같은 함수 increment를 실행하지만 this 칸이 undefined입니다. 다음 줄의 this.count에서 TypeError가 납니다." />

## 예제 1 — 기본: 그림과 코드를 맞춰 보기

Fig 1-1을 만든 코드입니다. 그림을 먼저 보고, 각 줄이 그림의 어디를 만드는지 맞춰 보세요.

<div class="code-title"><span>cart.ts, 기본 예제</span><span class="badge real">Node.js 22에서 실행 확인</span></div>

```ts
class Cart {
  owner: string;
  items: string[];
  constructor(owner: string, items: string[]) {
    this.owner = owner;
    this.items = items;
  }
  add(x: string) {
    this.items.push(x);
  }
}

const a = new Cart("민수", []);
const b = new Cart("지영", []);
a.add("사과");
b.add("우유");
console.log(a.items);
console.log(a.items === b.items, a.add === b.add);
console.log(Object.getOwnPropertyNames(a));
```

- **부르는 쪽에서**: 장바구니마다 `new Cart("민수", [])`처럼 새 배열을 넘깁니다.
- **받는 쪽에서(방어적 복사)**: 생성자에서 `this.items = [...items];`로 복사해 자기 배열을 만듭니다. 바깥에서 무엇을 넘기든 안전합니다.

## 비교와 트레이드오프

**메서드를 두는 두 가지 방법**

| 기준 | 프로토타입 메서드 `add() {…}` | 화살표 함수 필드 `add = () => {…}` |
|---|---|---|
| 그림에서의 위치 | Cart.prototype에 1개 | 인스턴스마다 1개씩 |
| 인스턴스 1000개일 때 함수 객체 | 1개 | 1000개 |
| this | 호출 식이 정함 (꺼내면 잃어버림) | 만들 때 고정 (꺼내도 안전) |
| 상속에서 재정의(3강) | 자연스러움 | 어색함 |

**참조를 다루는 두 가지 방법**

| 기준 | 참조 그대로 보관 `this.items = items` | 방어적 복사 `this.items = [...items]` |
|---|---|---|
| 비용 | O(1), 화살표만 복사 | 원소 수 n에 대해 O(n) 시간과 공간 |
| 안전성 | 바깥에서 같은 배열을 바꾸면 영향받음 | 바깥과 분리됨 |
| 깊이 | 해당 없음 | 한 단계만 복사(얕은 복사). 원소가 객체면 그 객체는 여전히 공유 |

**언어마다 그림이 조금 다릅니다.** Java와 C#은 메서드를 클래스에 두고 인스턴스가 클래스를 가리킵니다. Python도 인스턴스가 클래스를 가리키고 메서드를 클래스에서 찾습니다. JavaScript는 이 연결을 프로토타입이라는 평범한 객체로 합니다. "인스턴스에는 상태, 공유되는 곳에는 행동"이라는 큰 그림은 모두 같습니다.

<Layer n={7} />
## 실무에서는

- **this 손실은 콜백에서 가장 자주 일어납니다.** `button.addEventListener('click', counter.increment)`, `setTimeout(counter.increment, 100)`, `items.forEach(cart.add)`처럼 메서드를 다른 함수에 넘기는 순간 점 왼쪽이 사라집니다. `() => counter.increment()`로 감싸거나 bind를 씁니다. React가 클래스 컴포넌트를 쓰던 시절 생성자에서 `this.handleClick = this.handleClick.bind(this)`를 쓰거나 핸들러를 화살표 함수 필드로 선언한 이유가 바로 이것입니다.
- **생성자로 받은 배열과 객체는 복사할지 먼저 정합니다.** 바깥에서 계속 쓸 수 있는 값이면 `[...items]`나 `structuredClone(obj)`로 복사합니다. 복사하지 않기로 했다면 "이 객체는 넘겨받은 배열을 공유한다"고 문서에 적습니다.
- **바뀌면 안 되는 칸은 `readonly`로 표시합니다.** `readonly items: string[]`은 화살표를 바꾸는 대입만 막고, 배열 내용 변경은 막지 않습니다. 내용까지 막으려면 타입을 `readonly string[]`으로 씁니다.
- **그림부터 그립니다.** 설계 회의나 코드 리뷰에서 객체 관계가 헷갈리면 이 강의의 객체 다이어그램이나 UML 객체 다이어그램을 화이트보드에 그리는 것이 가장 빠릅니다.

## 더 깊이

- **ECMAScript 명세**: 일반 객체의 속성 읽기는 명세의 OrdinaryGet 절차입니다. 자기 속성에 없으면 [[Prototype]]의 [[Get]]을 다시 부르는 재귀가 그대로 적혀 있습니다. this가 정해지는 규칙은 함수 호출 평가(EvaluateCall)와 함수의 ThisMode(엄격 모드 여부)에 있습니다.
- **엔진의 최적화**: V8 같은 엔진은 같은 모양의 객체를 히든 클래스(hidden class, V8 내부 이름은 Map)로 묶고, 인라인 캐시(inline cache)로 "a.add는 늘 저 프로토타입에 있다"를 기억해 탐색을 빠르게 합니다. 생성자에서 항상 같은 순서로 칸을 만드는 습관이 성능에도 좋은 이유입니다.
- **TypeScript 설정**: 클래스 필드가 컴파일될 때 대입으로 바뀌는지 정의(define)로 바뀌는지는 `useDefineForClassFields` 옵션이 정합니다. 컴파일 대상이 ES2022 이상이면 표준 동작인 define이 기본입니다.
- **다음 강의(2강 캡슐화)**: 지금은 누구나 `a.items = []`로 장바구니를 비울 수 있습니다. 그림의 칸에 자물쇠를 다는 방법(`private`, `#items`)과 둘의 차이를 배웁니다.
