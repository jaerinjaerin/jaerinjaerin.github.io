## 문제부터 시작해 봅시다

쇼핑몰의 장바구니를 클래스로 만들었습니다. 민수와 지영이 각자 물건을 하나씩 담습니다.

```python
class Cart:
    items = []
    def __init__(self, owner):
        self.owner = owner
    def add(self, x):
        self.items.append(x)

a = Cart("민수")
b = Cart("지영")
a.add("사과")
b.add("우유")
print(a.items)
```

실행하면 에러 없이 `['사과', '우유']`가 나옵니다. 민수의 장바구니에 지영의 우유가 들어 있습니다. 이 강의를 마치면 이 결과가 왜 나오는지 메모리 그림으로 설명하고, 고칠 수 있게 됩니다.

## 비유: 붕어빵 틀, 그리고 비유가 틀리는 곳

클래스(Class)는 붕어빵 틀이고, 객체(Object)는 그 틀로 찍어낸 붕어빵이라는 비유를 많이 씁니다. 틀 하나로 팥 붕어빵도 슈크림 붕어빵도 만들 수 있으니, 출발점으로는 괜찮습니다.

<Callout kind="limit" title="이 비유가 맞지 않는 지점">
붕어빵은 다 구워지면 틀과 상관이 없어집니다. Python 객체는 다릅니다. 만들어진 뒤에도 자기 클래스를 계속 가리키고, 메서드나 속성이 필요할 때마다 클래스에 가서 찾아옵니다. 그래서 틀(클래스)에 무언가를 넣어 두면 모든 붕어빵이 그것을 함께 쓰게 됩니다. 이 강의의 버그는 전부 이 차이에서 생깁니다.
</Callout>

## 정확한 정의

- **객체(Object)**: 다음 세 요소로 이루어진 단위입니다.
  - **상태(State)**: 속성(attribute)에 담긴 데이터
  - **행동(Behavior)**: 메서드(method)
  - **정체성(Identity)**: 값이 같아도 서로 다른 객체임을 구분하는 고유성. Python에서는 `id()`로 확인하고 `is`로 비교합니다.
- **클래스(Class)**: 객체의 타입을 정의하는 템플릿입니다. 그 타입의 객체가 어떤 속성과 메서드를 가질지 정합니다. Python에서는 클래스 자신도 객체입니다.
- **인스턴스(Instance)**: 특정 클래스로 만든 객체입니다. "a는 Cart의 인스턴스다"라고 말합니다. `isinstance(a, Cart)`가 `True`입니다.
- **인스턴스 변수(instance variable)**: 인스턴스 각자의 `__dict__`에 저장된 속성입니다. `self.owner = ...`로 만듭니다.
- **클래스 변수(class variable)**: 클래스의 `__dict__`에 저장된 속성입니다. 클래스 몸체에 직접 쓴 `items = []`가 이것이고, 모든 인스턴스가 공유합니다.
- **객체지향 프로그래밍(OOP)**: 데이터와 그 데이터를 다루는 함수를 객체로 묶고, 객체끼리 메서드 호출(메시지)을 주고받게 해서 프로그램을 구성하는 패러다임입니다.

## 왜 객체지향이 생겼나

절차지향(Procedural) 프로그래밍에서는 데이터와 함수가 따로 있습니다.

```python
balance = 0

def deposit(amount):
    global balance
    balance += amount
```

작은 프로그램에서는 문제가 없지만 규모가 커지면 세 가지 문제가 드러납니다.

1. **누구나 데이터를 바꿀 수 있다.** 프로그램 어디에서든 `balance = -999`라고 쓸 수 있고, 막을 방법이 없습니다.
2. **같은 종류의 데이터가 여러 개가 되면 관리가 어렵다.** 계좌가 100개가 되면 잔액을 어디에 두고, 어떤 함수가 어느 계좌를 다루는지 직접 맞춰야 합니다.
3. **변경이 멀리 퍼진다.** 잔액의 형식을 바꾸면 그 데이터를 만지는 모든 함수를 찾아 고쳐야 합니다.

<Callout kind="note" title="역사 한 줄">
1967년 노르웨이의 Simula 67이 시뮬레이션 속 "사물"을 표현하려고 클래스와 객체를 처음 도입했습니다. 1970년대 Alan Kay의 Smalltalk는 "객체끼리 메시지를 주고받는다"는 모델로 이를 발전시켰고, 이후 C++, Java, Python이 이 생각을 이어받았습니다.
</Callout>

객체지향의 해법은 **데이터와 그 데이터를 지키는 규칙을 한곳에 두는 것**입니다. 계좌 객체가 자기 잔액을 갖고, 잔액을 바꾸는 유일한 통로인 `deposit` 메서드가 규칙(음수 입금 금지)을 검사합니다.

## 예제 1 — 기본: 은행 계좌

    bank_name = "OOP은행"

print(a.bank_name, b.bank_name)
print(a.__dict__)
print(a is b, isinstance(a, Account))

## 내부 동작: 객체가 만들어지고 메서드가 불리기까지

예제 1을 짧게 줄인 코드로, 실제로 메모리에서 일어나는 일을 단계별로 따라가 봅시다.

```python
class Counter:
    def __init__(self, start):
        self.count = start
    def increment(self):
        self.count += 1

c = Counter(5)
c.increment()
```

**1단계. class 문 실행.** 힙(heap, 객체들이 사는 메모리 영역)에 클래스 객체 `Counter`가 생깁니다. 그 객체의 `__dict__`에는 `'__init__'`과 `'increment'`라는 이름으로 함수 두 개가 저장됩니다. 전역 이름 `Counter`가 이 클래스 객체를 가리킵니다.

**2단계. Counter(5) 호출.**

1. `Counter.__new__(Counter)`가 힙에 빈 인스턴스를 만듭니다. 이 인스턴스는 자기 클래스가 `Counter`라는 것을 기억합니다(`type(c)`). `__dict__`는 아직 `{}`입니다.
2. `Counter.__init__(그_인스턴스, 5)`가 호출됩니다. 이 호출의 프레임(frame, 함수 실행 중 지역 변수가 사는 곳)에서 `self`는 방금 만든 인스턴스를, `start`는 5를 가리킵니다.
3. `self.count = start`가 실행되어 인스턴스의 `__dict__`가 `{'count': 5}`가 됩니다.
4. `__init__`이 끝나면 프레임이 사라지고, 완성된 인스턴스가 반환되어 전역 이름 `c`가 그것을 가리킵니다. `c`는 객체 자체가 아니라 객체를 가리키는 참조(reference)입니다.

**3단계. c.increment() 호출, 속성 탐색(attribute lookup).**

1. `c.__dict__`에서 `'increment'`를 찾습니다. 없습니다.
2. `type(c).__dict__`, 즉 `Counter.__dict__`에서 찾습니다. 함수가 있습니다.
3. 함수를 그냥 돌려주지 않고, 함수와 `c`를 묶은 바운드 메서드(bound method)를 만듭니다. 실제로 `print(c.increment)`를 하면 `<bound method Counter.increment of <__main__.Counter object at 0x...>>`가 나옵니다.
4. 바운드 메서드를 호출하면 결국 `Counter.increment(c)`가 실행됩니다. 이것이 self의 정체입니다.

<Callout kind="tip" title="이 강의의 핵심 규칙 두 가지">
<strong>읽기</strong>(<code>self.x</code>, <code>a.x</code>): 인스턴스의 <code>__dict__</code>를 먼저 보고, 없으면 클래스의 <code>__dict__</code>를 봅니다.<br />
<strong>대입</strong>(<code>self.x = ...</code>): 클래스를 보지 않고 언제나 인스턴스의 <code>__dict__</code>에 씁니다.<br />
<code>self.items.append(x)</code>는 대입이 아니라 <strong>읽기 + 변경(mutation)</strong>이라는 점에 주의하세요.
</Callout>

## 경계와 실패: 실제 오류 메시지 읽기

<Callout kind="error" title="self를 빼먹었을 때">
<code>TypeError: Counter.increment() takes 0 positional arguments but 1 was given</code><br />
<code>def increment():</code>처럼 self를 빼고 정의한 뒤 <code>c.increment()</code>를 호출한 경우입니다. 나는 인자를 하나도 안 넘겼는데 "1개가 넘어왔다"고 합니다. 3단계에서 Python이 인스턴스를 첫 인자로 자동으로 넘기는데, 받을 자리가 없기 때문입니다.
</Callout>

<Callout kind="error" title="__init__에 필요한 인자를 빠뜨렸을 때">
<code>TypeError: Counter.__init__() missing 1 required positional argument: 'start'</code><br />
<code>Counter()</code>처럼 호출한 경우입니다. 클래스를 호출할 때 넘긴 인자는 그대로 <code>__init__</code>에 전달됩니다. self는 자동으로 채워지므로 빠진 것은 start입니다.
</Callout>

<Callout kind="error" title="속성 이름을 잘못 썼을 때">
<code>AttributeError: 'Counter' object has no attribute 'cout'. Did you mean: 'count'?</code><br />
<code>c.cout</code>처럼 오타를 낸 경우입니다. 인스턴스의 <code>__dict__</code>와 클래스의 <code>__dict__</code> 모두에서 찾지 못했습니다. "Did you mean" 제안은 Python 3.10부터 트레이스백에 표시되며, 철자가 충분히 비슷할 때만 나옵니다(<code>c.cnt</code>에는 나오지 않습니다).
</Callout>

<Callout kind="error" title="클래스에서 인스턴스 변수를 찾을 때">
<code>AttributeError: type object 'Cart' has no attribute 'items'</code><br />
정상 모드의 Cart에서 <code>Cart.items</code>를 읽은 경우입니다. 인스턴스 변수는 인스턴스에만 있습니다. 탐색은 인스턴스에서 클래스로 올라갈 뿐, 클래스에서 인스턴스로 내려가지 않습니다.
</Callout>

가장 위험한 경우는 **오류가 나지 않는 경우**입니다. 예제 2처럼 가변 클래스 변수를 공유하면 프로그램은 멀쩡히 돌면서 틀린 결과를 냅니다. 같은 원리의 함정이 하나 더 있습니다.

```python
def __init__(self, owner, items=[]):
    self.owner = owner
    self.items = items
```

기본 인자 `[]`는 함수를 **정의할 때 한 번** 만들어져 함수 객체에 저장됩니다. 그래서 `items`를 넘기지 않은 모든 인스턴스가 같은 리스트를 공유합니다. 관례적인 해결책은 `items=None`으로 받고 함수 안에서 `self.items = [] if items is None else list(items)`처럼 새로 만드는 것입니다.

## 비교와 트레이드오프

| 기준 | 절차지향 | 객체지향 | 함수형 |
|---|---|---|---|
| 데이터와 함수 | 분리 | 객체로 묶음 | 분리, 데이터는 보통 불변 |
| 상태 변경 | 전역 데이터를 직접 변경 | 객체가 자기 상태를 변경 | 새 값을 만들어 반환 |
| 잘 맞는 곳 | 짧은 스크립트, 단순한 처리 흐름 | 상태를 가진 사물이 많은 도메인 | 데이터 변환, 동시성, 테스트 |
| 흔한 문제 | 규모가 커지면 변경이 멀리 퍼짐 | 숨은 공유 상태, 과한 클래스 설계 | 상태가 많은 UI·입출력에서 어색함 |

클래스 변수와 인스턴스 변수도 비교해 봅시다.

| 기준 | 클래스 변수 | 인스턴스 변수 |
|---|---|---|
| 저장 위치 | 클래스의 `__dict__` 1곳 | 인스턴스마다의 `__dict__` |
| 만들어지는 때 | class 문 실행 시 1번 | `__init__` 실행마다 |
| 메모리 | 인스턴스 수와 무관 | 인스턴스 수에 비례 |
| 알맞은 값 | 상수, 의도적으로 공유하는 설정 | 객체마다 다른 상태 |

**비용 측면**
- **공간**: 인스턴스마다 `__dict__`라는 딕셔너리를 가집니다. CPython은 같은 클래스의 인스턴스들이 키를 공유하는 최적화(PEP 412 키 공유 딕셔너리)를 쓰지만, 그래도 객체를 수백만 개 만들면 부담이 됩니다. 이때 `__slots__`를 선언하면 `__dict__` 대신 고정된 칸만 두어 메모리를 줄일 수 있습니다. 대신 정해 둔 이름 외의 속성은 추가할 수 없습니다.
- **시간**: 속성 탐색은 딕셔너리 조회라 평균 O(1)이지만, 인스턴스, 클래스, (상속하면) 부모 클래스로 여러 단계를 거칠 수 있습니다. 그래서 아주 뜨거운 반복문에서는 메서드를 지역 변수에 담아 두는 최적화를 하기도 합니다.

## 실무에서는

- **가변 객체(list, dict, set)는 `__init__` 안에서 만듭니다.** 리뷰에서 가장 자주 지적되는 실수 중 하나입니다. 린터(pylint의 dangerous-default-value 경고 등)도 가변 기본 인자를 잡아 줍니다.
- **클래스 변수는 상수나 의도적인 공유에만 씁니다.** 예: 은행 이름, 기본 설정값, 만들어진 인스턴스 수를 세는 카운터.
- **데이터를 담는 클래스는 `@dataclass`를 자주 씁니다.** `__init__`을 자동으로 만들어 주고, `items: list = []`처럼 가변 기본값을 쓰면 `ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory`로 막아 줍니다. 대신 `field(default_factory=list)`를 씁니다.
- **객체지향은 도구입니다.** Django의 모델, 게임의 캐릭터처럼 상태를 가진 사물을 표현할 때 강력하지만, 단순한 계산은 함수 하나가 더 낫습니다. 클래스를 만들기 전에 "이 데이터에 지켜야 할 규칙이 있는가"를 먼저 물어보세요.

## 더 깊이

- **Python 공식 문서의 Data model 장**: `__new__`, `__init__`, `__dict__`, 속성 접근 규칙의 공식 정의가 있습니다.
- **디스크립터 프로토콜(Descriptor protocol)**: `c.increment`에서 함수가 바운드 메서드로 바뀌는 진짜 원리입니다. 함수 객체의 `__get__` 메서드가 그 일을 합니다. 공식 문서의 Descriptor HowTo Guide가 좋은 출발점입니다.
- **메타클래스(Metaclass)**: 클래스도 객체라면 클래스를 만드는 것은 무엇일까요? 답은 `type`입니다. `Counter(5)`가 동작하는 것도 `type.__call__`이 `__new__`와 `__init__`을 차례로 부르기 때문입니다.
- **다음 강의**: 2강 캡슐화에서는 `a.balance = -999`를 어떻게 막는지, 그리고 Python이 왜 Java처럼 private을 강제하지 않는지 다룹니다.
