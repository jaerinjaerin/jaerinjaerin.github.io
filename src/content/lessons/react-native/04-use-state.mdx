## 문제부터 시작해 봅시다

좋아요 버튼을 만들었습니다. 버튼을 누를 때마다 숫자를 1씩 올리고 싶어서 이렇게 썼어요.

```jsx
export default function Like() {
  let likes = 0;
  return <Button title={`좋아요 ${likes}`} onPress={() => { likes = likes + 1; }} />;
}
```

버튼을 아무리 눌러도 화면은 계속 `좋아요 0`입니다. `likes`는 분명 1, 2, 3으로 늘어났을 텐데 왜 화면은 그대로일까요? 이 강의는 이 질문에 정확히 답하는 것에서 시작합니다.

## 비유: 사진관과 주문서

React 컴포넌트를 **사진관**이라고 생각해 봅시다.

- 컴포넌트 함수를 한 번 실행하는 것(**렌더링**)은 사진을 **한 장 찍는 것**입니다. 화면은 그 사진입니다.
- 사진 속 숫자는 찍는 순간 고정됩니다. 사진을 들고 펜으로 숫자를 고쳐 써도(일반 변수 수정) 벽에 걸린 사진은 바뀌지 않습니다.
- **State**는 사진관 금고에 보관된 장부입니다. 사진을 찍을 때마다 사진사는 금고의 장부를 보고 숫자를 넣습니다.
- **setState**는 장부를 직접 고치는 펜이 아니라 **"다음 사진은 이 숫자로 찍어 주세요"라는 주문서**입니다. 주문서를 여러 장 내면 사진사는 모아 두었다가, 순서대로 처리하고 **새 사진을 한 장** 찍습니다.

<Callout kind="limit" title="이 비유가 맞지 않는 지점">
실제 React는 "사진 전체"를 새로 거는 것이 아니라, 이전 결과와 비교해 <strong>바뀐 부분만</strong> 화면(네이티브 뷰)에 반영합니다. 또 주문서는 그냥 "숫자"일 수도 있고, "지금 숫자에 1을 더해 주세요" 같은 <strong>계산 방법(함수)</strong>일 수도 있습니다. 이 차이가 이 강의의 핵심입니다.
</Callout>

## 정확한 정의

- **렌더링(rendering)**: React가 컴포넌트 함수를 호출해, 화면이 어떻게 보여야 하는지(React 요소 트리)를 계산하는 일입니다. 함수가 반환한 JSX가 결과입니다.
- **State(상태)**: 컴포넌트가 **렌더와 렌더 사이에 기억해야 하는 값**입니다. 컴포넌트 함수 안의 지역 변수가 아니라, React가 컴포넌트 바깥(컴포넌트 인스턴스에 연결된 저장소)에 보관합니다.
- **useState**: State를 하나 선언하는 **Hook**입니다. `const [state, setState] = useState(initialValue)` 형태로 쓰고, **[현재 렌더의 값, 업데이트 함수]** 두 개짜리 배열을 반환합니다.
- **setState(nextState)**: State 변경을 **예약**하고 **다시 렌더링을 요청**하는 함수입니다. 인자로 값(`setCount(5)`)을 주면 그 값으로 교체하고, 함수(`setCount(c => c + 1)`)를 주면 직전 값을 받아 다음 값을 계산합니다.
- **스냅샷(snapshot)**: 한 번의 렌더에서 State 값은 **상수처럼 고정**됩니다. 그 렌더에서 만들어진 이벤트 핸들러도 그 값을 기억합니다(클로저).

## 왜 State가 필요한가: 일반 변수가 실패하는 두 가지 이유

처음 코드가 실패한 이유는 정확히 두 가지입니다.

1. **바꿔도 아무도 다시 그리지 않는다.** `likes = likes + 1`은 JavaScript 변수 하나를 바꿀 뿐, React에게 "화면을 다시 계산하라"고 알리지 않습니다. React는 언제 다시 렌더링해야 하는지 모릅니다.
2. **다시 그려도 값이 사라진다.** 설령 다른 이유로 다시 렌더링되더라도, 컴포넌트 함수가 처음부터 다시 실행되면서 `let likes = 0`이 또 실행됩니다. 지역 변수는 함수가 끝나면 사라지기 때문입니다.

useState는 이 두 문제를 동시에 해결합니다. 값을 **React가 함수 바깥에 보관**하고(문제 2 해결), 값을 바꾸는 유일한 통로인 **setState가 다시 렌더링을 요청**합니다(문제 1 해결).

<Callout kind="note" title="역사 한 줄">
2019년 React 16.8 이전에는 State를 쓰려면 클래스 컴포넌트에서 <code>this.state</code>와 <code>this.setState</code>를 써야 했습니다. Hook은 함수 컴포넌트에서도 State 같은 React 기능을 쓸 수 있게 하려고 만들어졌습니다.
</Callout>

## 내부 동작: 버튼을 누른 순간부터 화면이 바뀌기까지

`+1`을 누르면 내부에서 다음 일이 **순서대로** 일어납니다. 먼저 그림으로 전체 흐름을 본 뒤, 단계별로 정확히 짚어 보겠습니다.

<UseStateMachineFigure />

1. **이벤트 처리** — 네이티브 쪽 터치 이벤트가 JavaScript로 전달되고, onPress에 등록된 화살표 함수가 실행됩니다. 이 함수는 **직전 렌더에서 만들어졌기 때문에** 그 렌더의 `count`(예: 0)를 기억합니다.
2. **업데이트 예약** — `setCount(count + 1)`이 실행됩니다. 괄호 안의 `count + 1`이 **먼저 계산**되어 1이 되고, React는 이 컴포넌트의 State 큐에 "다음엔 1"이라는 **업데이트**를 넣습니다. 이 시점에 `count` 변수는 여전히 0이고, 화면도 그대로입니다.
3. **배칭(batching)** — 이벤트 핸들러가 끝날 때까지 React는 기다립니다. 핸들러 안에서 setState를 여러 번 불러도 모아 두었다가 **렌더링을 한 번만** 예약합니다. React 18부터는 setTimeout이나 Promise 안의 업데이트도 자동으로 묶습니다(React Native는 새 아키텍처 기준).
4. **렌더 단계** — React가 `App()`을 다시 호출합니다. `useState(0)`에 도달하면 초기값 0은 무시하고, 보관 중인 값에서 출발해 **큐에 쌓인 업데이트를 순서대로 적용**합니다. 값 업데이트는 결과를 **교체**하고, 함수 업데이트는 **직전 결과를 넣어 계산**합니다. 최종값이 이번 렌더의 새 스냅샷 `count`가 됩니다.
5. **비교와 커밋** — 새로 계산한 JSX를 이전 결과와 비교해, 바뀐 부분(여기서는 Text의 글자)만 네이티브 뷰에 반영합니다. 이제야 화면에 1이 보입니다.

React 소스 코드(`ReactFiberHooks.js`)에서 4번의 "순서대로 적용"은 사실상 아래 한 줄짜리 함수로 이루어집니다.

```js
function basicStateReducer(state, action) {
  return typeof action === 'function' ? action(state) : action;
}
```

`action`이 함수면 직전 `state`를 넣어 실행하고, 아니면 그 값으로 교체합니다. 즉 **useState는 이 리듀서를 쓰는 useReducer**와 같습니다.

### State는 어디에 저장될까: Hook 목록

React는 화면의 컴포넌트 하나하나마다 내부 객체(**Fiber**)를 두고, 그 안에 Hook들을 **호출된 순서대로 연결 리스트**로 저장합니다. 각 칸(hook)에는 현재 값(`memoizedState`)과 업데이트 큐(`queue`)가 있습니다.

중요한 점은, 칸에 **변수 이름이 저장되지 않는다**는 것입니다. React는 "이 컴포넌트에서 **첫 번째**로 호출된 useState", "**두 번째**로 호출된 useState"처럼 **순서로만** 칸을 찾습니다. 그래서 렌더마다 Hook 호출 순서가 같아야 합니다. 아래 두 번째 실습에서 이 순서가 깨지는 순간을 직접 보게 됩니다.

## 예제 2 — 함정: "3 올리기" 버튼의 버그와 수정

<div class="code-title"><span>LikeButton.js — 함정 예제</span><span class="badge real">그대로 실행 가능</span></div>

```jsx
import { useState } from 'react';
import { View, Text, Button } from 'react-native';

export default function LikeButton() {
  const [likes, setLikes] = useState(0);

  function addThree() {
    setLikes(likes + 1);
    setLikes(likes + 1);
    setLikes(likes + 1);
    console.log('방금 누른 뒤 likes =', likes);
  }

  function addThreeLater() {
    setTimeout(() => {
      setLikes(likes + 3);
    }, 2000);
  }

  return (
    <View style={{ padding: 24, gap: 12 }}>
      <Text style={{ fontSize: 32 }}>❤️ {likes}</Text>
      <Button title="+3 (버그)" onPress={addThree} />
      <Button title="2초 뒤 +3 (버그)" onPress={addThreeLater} />
    </View>
  );
}
```

고친 코드는 다음과 같습니다. **이전 값을 기준으로 다음 값을 계산할 때는 항상 함수형 업데이트**를 씁니다.

  setLikes(prev => prev + 1);

function addThreeLater() {

## 경계와 실패: 실제로 만나는 오류들

### 1) 렌더 도중 setState 호출 → 무한 렌더링

```jsx
<Button title="+1" onPress={setCount(count + 1)} />
```

<Callout kind="error" title="실제 오류 메시지">
<code>Too many re-renders. React limits the number of renders to prevent an infinite loop.</code>
</Callout>

`onPress={setCount(count + 1)}`는 "누르면 실행할 함수"를 넘기는 것이 아니라, **렌더하는 도중에 setCount를 바로 호출**한 뒤 그 반환값(undefined)을 넘깁니다. setCount가 다시 렌더를 요청하고, 다시 렌더하면 또 호출하고… 끝없이 반복됩니다. 해결: `onPress={() => setCount(count + 1)}`.

### 2) 조건문·반복문 안에서 Hook 호출

<Callout kind="error" title="실제 오류 메시지 (개발 모드)">
<code>Rendered fewer hooks than expected. This may be caused by an accidental early return statement.</code><br />
<code>Rendered more hooks than during the previous render.</code><br />
ESLint(eslint-plugin-react-hooks): <code>React Hook "useState" is called conditionally. React Hooks must be called in the exact same order in every component render.</code>
</Callout>

Hook은 순서로 저장되기 때문에, 어떤 렌더에서 호출을 하나 건너뛰면 뒤의 Hook들이 **한 칸씩 밀려 남의 값을 받습니다.** 아래 실습에서 직접 확인하세요.

### 3) 배열·객체를 직접 수정 → 화면이 안 바뀜

```jsx
const [todos, setTodos] = useState([]);

function add(text) {
  todos.push({ id: Date.now(), text }); // ❌ 기존 배열을 직접 수정
  setTodos(todos);                       // 같은 배열을 다시 넘김
}
```

React는 새 State가 이전과 같은지 `Object.is(이전, 다음)`으로 비교합니다. 배열 안을 바꿔도 **배열 자체(참조)는 같으므로** "바뀐 것이 없다"고 판단하고 다시 렌더링하지 않을 수 있습니다. 반드시 새 배열을 만들어 넘깁니다: `setTodos(prev => [...prev, { id: Date.now(), text }])`. 객체도 마찬가지로 `setUser(prev => ({ ...prev, name: '지연' }))`처럼 새 객체를 만듭니다. (9강 전개 구문에서 자세히 다룹니다.)

### 4) 비싼 초기값을 매 렌더마다 계산

`useState(loadBigList())`는 초기값이 첫 렌더에서만 쓰이는데도, **함수 호출 자체는 매 렌더마다** 일어납니다. `useState(() => loadBigList())`처럼 **함수를 넘기면(지연 초기화)** 첫 렌더에서만 실행됩니다.

### 5) 같은 값으로 setState

`setCount(count)`처럼 이전과 같은 값(Object.is 기준)을 넣으면 React는 다시 렌더링을 건너뛸 수 있습니다. 오류는 아니지만, "왜 렌더가 안 일어나지?"라는 혼란의 원인이 됩니다.

## 비교와 트레이드오프: 무엇을 언제 쓰나

| 방법 | 렌더 사이에 값 유지 | 바꾸면 다시 렌더링 | 언제 쓰나 |
|---|---|---|---|
| 일반 변수 `let x` | ✗ (매 렌더 초기화) | ✗ | 렌더 안에서 잠깐 계산하는 값 |
| `useState` | ✓ | ✓ | 화면에 보이거나 화면을 바꾸는 값 |
| `useRef` | ✓ | ✗ | 화면과 무관하게 기억할 값 (타이머 id, 이전 값, 입력창 참조) |
| `useReducer` | ✓ | ✓ | 업데이트 규칙이 복잡하거나 여러 State가 함께 바뀔 때 |
| 계산으로 파생 | — | — | 다른 State로 계산할 수 있는 값은 State로 만들지 않음 |

**값 업데이트 vs 함수형 업데이트**

| | `setCount(count + 1)` | `setCount(c => c + 1)` |
|---|---|---|
| 기준값 | 이 렌더의 스냅샷 | 큐에서 직전까지 계산된 값 |
| 연속 호출 | 마지막 값으로 덮어씀 | 누적됨 |
| 타이머·비동기 안 | 오래된 값 위험 | 실행 시점의 최신 값 |
| 적합한 경우 | 이전 값과 무관한 새 값 (`setOpen(false)`, `setText(입력값)`) | 이전 값에 의존 (`+1`, 토글 `v => !v`, 배열 추가) |

**비용 관점**: 핸들러에서 setState를 k번 호출하면 큐 처리는 O(k)이지만, 배칭 덕분에 **렌더링은 1번**입니다. 렌더링(컴포넌트 함수 실행 + 비교 + 네이티브 반영)이 큐 처리보다 훨씬 비싸므로, 배칭은 성능에 큰 이점입니다.

## 실무에서는

- **업데이트 함수의 인자 이름**은 관례적으로 `prev`나 State 이름의 첫 글자(`c`, `l`)를 씁니다. 리뷰어가 함수형 업데이트임을 바로 알 수 있습니다.
- **State는 최소한으로.** `items`와 `itemCount`를 둘 다 State로 두면 서로 어긋나는 버그가 생깁니다. `itemCount`는 `items.length`로 계산합니다.
- **가까운 곳에 둔다.** 한 컴포넌트에서만 쓰는 State는 그 컴포넌트에 둡니다. 여러 자식이 같은 값을 써야 할 때만 부모로 올립니다(6강 State + Props).
- **eslint-plugin-react-hooks**를 켭니다. 조건부 Hook 같은 실수를 실행 전에 잡아 줍니다.
- **React DevTools**(React Native는 Expo/React Native DevTools)에서 컴포넌트를 선택하면 Hook 목록과 현재 State 값을 볼 수 있습니다. 실습에서 본 "Hook 목록"이 실제로 보입니다.
- 폼처럼 State가 많고 서로 얽히면 `useReducer`나 폼 라이브러리를 검토합니다.

## 더 깊이 알아보기

- **React 소스**: `packages/react-reconciler/src/ReactFiberHooks.js`의 `mountState`(첫 렌더에 칸 생성), `updateReducer`(큐 처리), `dispatchSetState`(setState의 실체). 실습의 의사 코드는 이 흐름을 단순화한 것입니다. 실제 큐는 순환 연결 리스트이고, 업데이트마다 우선순위(lane)가 붙어 급한 업데이트를 먼저 처리할 수 있습니다.
- **이른 탈출(eager bailout)**: 큐가 비어 있을 때 setState가 호출되면, React는 다음 값을 미리 계산해 이전 값과 같으면 렌더 예약 자체를 생략하기도 합니다.
